## 0. 一句话目标

把 `messages_data/` 下 **6 个「全量读写」的 JSON 文件**，迁移到**单文件 SQLite**
（Node 24 内置 `node:sqlite`，**零安装**），并把「图片」从设置里拆出去走静态文件。

## 1. 为什么要做（问题量化，全部实测）

### 1.1 现状

| 文件 | 大小 | 结构 |
| :--- | :--- | :--- |
| `settings.json` | **0.50 MB** | `{userId: settings}`，**图片占 99.6%**（525 KB / 527 KB） |
| `messages_v2.json` | 0.20 MB | `{userId: messages[]}` |
| `model_limits.json` | 1.5 KB | `{模型名: 上限}`，61 条，**全局配置非按账号** |
| `active_sessions.json` | 391 B | `{userId: {mobile, desktop}}` |
| `users.json` | 144 B | 数组 `[{id, username, passwordHash}]` |
| `pending-decisions.json` | 67 B | `{version, savedAt, questions, approvals}` |

### 1.2 核心缺陷：为取一个字段，全量读整个文件

`server.ts:260` 的 `loadSettingsFile()` **没有任何缓存**，每次调用都：读磁盘 → `JSON.parse` → 分配全部账号的 base64 字符串 → 丢掉 99.9%。

而 **`GET /api/check-session`（`server.ts:1894`）** 是**每 4–30 秒每台设备轮询一次**的高频接口，它在 `server.ts:1907` 处**只为读一个 token 字段**就调了它：

```ts
// server.ts:1905-1912 —— 注释自己写着"这个接口每 4 秒被轮询一次"
const currentAgentToken = await (async () => {
  try {
    const allSettings = await loadSettingsFile();     // ← 全量读 + JSON.parse
    return readUserAgentToken(allSettings[userId]);   // ← 只为拿一个字符串
  } catch { return ""; }
})();
```

`loadSettingsFile()` 共 **12 处**调用点：行 1907（check-session）、2525（归属反查）、2600（GET 设置）、
2643（POST 设置）、2670（sync-settings）、3009（agent/register）、4220/4241（rotate-token）、
4338（bridge/current-token）、4460/4469（download-bat）、5336（Socket update_settings）。

`MESSAGES_FILE` 更密集：**9 处 `withFileLock`**、**12 处 `safeReadJSON`**，且**每条消息收发都要全量读写**。

### 1.3 多账号下的量级（这是做迁移的直接原因）

服务器**要给多个人使用**。按每账号 2 设备、每人 525 KB 图片估算：

| | 1 账号（现状） | 10 账号 | 20 账号 |
| :--- | :--- | :--- | :--- |
| `settings.json` | 0.5 MB | **5.25 MB** | **10.5 MB** |
| 全量读次数/分钟（推送连通，30s） | 4 | **40** | 80 |
| **每分钟读取量** | 2 MB | **210 MB** | **840 MB** |
| 若推送断开（退到 4s 轮询） | 15 MB/min | **1.5 GB/min** | **6 GB/min** |

且**写锁是全局的**（单文件 + `withFileLock`）：任何人改一次设置 → 全量重写 5–10 MB 并持锁，
**期间所有人的轮询全部排队**。AGENTS.md §9.5 记录的事故（6.14 MB 头像把写锁占死 → 桥接归属反查
403、SSE 被拖断）在多账号下会**变成常态**。

### 1.4 消息文件比设置文件更危险

| | `settings.json` | `messages_v2.json` |
| :--- | :--- | :--- |
| 读频率 | 每 4–30 秒 / 设备 | **每条消息收发** |
| 写频率 | 只有改设置时 | **每条消息收发** |
| 增长趋势 | 稳定（图片压进预算后就定了） | **持续累积，只增不减** |

**设置文件有天然天花板，消息文件没有**。所以两者**都要迁移**，不能只迁设置。

## 2. 技术选型：Node 24 内置 SQLite（已实测，零安装）

**环境实测（2026-09-29）**：

```
Node 版本            v24.15.0        （C:\nvm4w\nodejs\node.exe）
node:sqlite          ✓ 直接 require 可用，【无需】--experimental-sqlite flag
SQLite 引擎版本      3.51.3
WAL 模式             ✓ PRAGMA journal_mode = WAL 返回 wal
文件库 + 索引查询     ✓ 正常
```

**结论：一个东西都不用装。**

- ❌ 不需要 MySQL / PostgreSQL 服务
- ❌ 不需要 `npm install` 任何依赖
- ❌ 不需要端口、账号、密码、服务自启
- ✅ 就是一个 `.db` 文件，与现有 JSON 并排放在 `messages_data/`

```ts
import { DatabaseSync } from 'node:sqlite';
const db = new DatabaseSync('messages_data/lxai.db');
db.exec('PRAGMA journal_mode = WAL');
```

**为什么不用 Postgres/MySQL**：本项目是单机、单进程、数据量几十 MB 级。SQLite 在此规模不是"凑合"，
而是最合适的选择；引入独立数据库服务只增加运维负担（服务管理、端口、备份、升级），换不来收益。

**打包兼容性**：`npm run build` 用 `esbuild server.ts --bundle --platform=node --format=cjs --packages=external`。
`node:` 前缀是内置模块，esbuild 会保留为外部引用，**不会尝试打包**。构建后建议验证
`dist/server.cjs` 里 `require("node:sqlite")` 被原样保留。

## 5. 目标 Schema

```sql
PRAGMA journal_mode = WAL;      -- 并发读写必需

-- 设置：高频字段拆列，其余进 payload；图片【不进库】
CREATE TABLE IF NOT EXISTS settings (
  user_id              TEXT PRIMARY KEY,
  agent_token          TEXT,      -- check-session 只查这一列
  is_logged_in         INTEGER,
  payload              TEXT       -- 其余约 50 个字段的 JSON（含 apiEndpoints、systemPrompt、tts/asr 配置等）
);

CREATE TABLE IF NOT EXISTS messages (
  id                 TEXT PRIMARY KEY,
  user_id            TEXT NOT NULL,
  session_id         TEXT NOT NULL,
  role               TEXT,
  sender             TEXT,
  content            TEXT,
  text               TEXT,
  reasoning_content  TEXT,
  thought            TEXT,
  created_at         INTEGER,
  timestamp          INTEGER,
  elapsed_seconds    INTEGER,
  attachments        TEXT,        -- JSON
  status             TEXT,
  is_agent_mode      INTEGER,
  agent_execution    TEXT         -- JSON，可能很大：列表查询不要带它
);
CREATE INDEX IF NOT EXISTS idx_msg_user_session_created
  ON messages(user_id, session_id, created_at);
CREATE INDEX IF NOT EXISTS idx_msg_user_created
  ON messages(user_id, created_at DESC);

CREATE TABLE IF NOT EXISTS users (
  id            TEXT PRIMARY KEY,
  username      TEXT UNIQUE,
  password_hash TEXT
);

CREATE TABLE IF NOT EXISTS active_sessions (
  user_id           TEXT NOT NULL,
  device_type       TEXT NOT NULL,   -- 'mobile' | 'desktop'
  client_session_id TEXT,
  last_active       INTEGER,
  PRIMARY KEY (user_id, device_type)
);

CREATE TABLE IF NOT EXISTS model_limits (
  model_name TEXT PRIMARY KEY,
  max_tokens INTEGER
);

CREATE TABLE IF NOT EXISTS pending_decisions (
  id       TEXT PRIMARY KEY,   -- 'questions' / 'approvals' / ...
  payload  TEXT,
  saved_at INTEGER
);

-- 媒体文件索引（图片本体在磁盘，见阶段 4）
CREATE TABLE IF NOT EXISTS media_files (
  user_id    TEXT NOT NULL,
  field      TEXT NOT NULL,   -- userAvatar / aiAvatar / customBackground / splashImage
  rel_path   TEXT NOT NULL,   -- 相对 messages_media/settings-media/<userId>/ 的路径
  bytes      INTEGER,
  sha256     TEXT,
  updated_at INTEGER,
  PRIMARY KEY (user_id, field)
);
```

**为什么 `apiEndpoints` 放 payload 而不建表**：它只有 1 条 9 个字段、不在任何高频路径上。
建表会让"读设置"变成多表 join，收益为负。**若将来要做跨账号统计再拆**。

## 6. 五条设计要点（决定这次迁移成不成）

### ① 保持 `loadSettingsFile` / `saveSettingsFile` 的**签名与返回结构不变**
它们有 **12 处**调用点。只换内部实现（读库/写库），上层**一行都不用改** ——
这是把"大手术"降级成"换发动机"的关键。**返回结构必须与 JSON 时代完全一致**
（包括 `mapSettingsSecrets` 的解密行为、`sanitizeSettings` 的位置）。

### ② 图片**绝不进库**
数据库解决"整份读写"，**解决不了"图片占 99.6%"**。若塞进库会换来：
数据库文件膨胀、备份变慢、`SELECT *` 误伤把 525 KB base64 捞出来、连接被大字段占住。
图片走 `messages_media/settings-media/<userId>/<field>.jpg` 静态文件。

### ③ **API 契约不要变**（这条决定 App 要不要改）
阶段 4 有两种做法：
- ❌ 让 `GET /api/settings/:userId` 返回图片 URL → **App 必须跟着改**，风险扩散到客户端
- ✅ **服务端内部读文件后仍内联成 base64 返回** → **App 零改动**

**选后者**。对外契约不变，图片存储怎么改都是服务端内部的事。

### ④ 消息查询**必须分页**
否则只是把"读整个文件"翻译成"读整张表"，问题照旧。列表/预览查询要：
- 按 `(user_id, session_id, created_at DESC)` 走索引 + `LIMIT`
- **不要 `SELECT *`**（会带上 `agent_execution` 大字段）
- 需要过程数据时**单独按 id 查**

### ⑤ 写路径必须走**事务**
JSON 时代靠 `withFileLock` 保证"读-改-写"原子性。换成数据库后，等价物是**事务**
（`db.exec('BEGIN IMMEDIATE')` … `COMMIT`），尤其 `saveSettingsFile` 的"读全量→改一条→写全量"
这类模式。**不要让两个请求交错读改写**。

## 7. 分阶段实施（每阶段独立可验证、可回退）

### 阶段 1：建库 + 迁移数据（**不碰任何运行中的代码**）⭐ 建议先只做这一步

- 新增脚本 `tools/migrate-to-sqlite.mjs`（**只读 6 个 JSON + 新建 `.db`**）
- 流程：读 JSON → 建表 → 灌数据 → 图片写盘 → 输出**校验报告**
- **不修改 `server.ts`、不重启服务、不影响线上**
- 产出：`messages_data/lxai.db` + `messages_media/settings-media/<userId>/*.jpg`
- 校验报告应包含：每表行数 vs JSON 条数、抽样字段逐字比对、图片 sha256 与 base64 长度比对

**这一步做完就能看到真实收益**（例如 `settings.json` 5 MB → 库里几十 KB，因为图片不进库），
再决定要不要继续。

### 阶段 2：换存储层（保持函数签名）
- 改 `loadSettingsFile` / `saveSettingsFile` 内部 → 查库/写库（保持返回结构，见要点 ①）
- 改 `MESSAGES_FILE` 的 9 处 `withFileLock` + 12 处 `safeReadJSON` → 对应 SQL
- `users` / `active_sessions` / `model_limits` / `pending_decisions` 同步替换
- 验证：`npm run lint`（= `tsc --noEmit`）**0 error** → 启动 → 跑通一遍完整功能

### 阶段 3：高频路径专用查询（收益最大的一步）
- `check-session`（行 1907）改用：
  ```ts
  const getUserAgentToken = (userId: string): string =>
    db.prepare('SELECT agent_token FROM settings WHERE user_id = ?').get(userId)?.agent_token ?? '';
  ```
- 同理给 `resolveTokenOwnerUserId`（行 2525）加专用索引查询
- **此阶段的收益**：高频读从"每分钟 210 MB"直接降到"每次一条主键查询"

### 阶段 4：图片独立存储
- 图片写盘 + `media_files` 表登记
- `GET /api/settings/:userId` 内部读文件后**仍内联 base64 返回**（要点 ③，App 零改动）
- 静态路由（若将来想直接给客户端 URL 用）：`app.use('/media/settings', express.static(...))`
- 旧的 `settings.payload` 里的图片字段要**清理掉**（否则体积没降）

### 阶段 5：切换上线
见 §10。**任何一步出问题都能回到 JSON**（见 §9）。
