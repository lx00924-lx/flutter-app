## 2. 已经过时的部分（照本文改）

### 2.1 要迁的文件：6 个 → 9 个

原版 §0 和 §1.1 列了 6 个文件。**现在实际有 9 个**（实测大小，已排除 `.bak` / `.corrupt` 等历史残骸）：

| 文件 | 现在大小 | 原版有没有 | 说明 |
| :--- | ---: | :--- | :--- |
| `settings.json` | **490,011 B** | ✅ | 图片占 99.5% |
| `messages_v2.json` | **145,973 B** | ✅ | 2 个账号共 13 条消息 |
| `model_limits.json` | 1,516 B | ✅ | 全局配置，非按账号 |
| `active_sessions.json` | 659 B | ✅ | 2 账号 × 2 设备槽位，带 `version` / `lastActive` |
| `users.json` | 372 B | ✅ | **2 个账号**（原版时是 1 个） |
| `pending-decisions.json` | 67 B | ✅ | 全是空结构（回答完就清） |
| **`sessions_v2.json`** | **583 B** | ❌ **原版完全没有** | 会话表 |
| **`deletion_signals.json`** | **755 B** | ❌ **原版完全没有** | 删除信号 |
| **`login_attempts.json`** | **51 B** | ❌ **原版完全没有** | 登录失败计数 |

⚠️ **`sessions_v2.json` 是最大的一块新增**：它是消息的父表，迁移时**必须和 `messages_v2.json` 一起迁**，否则 `sessionId` 关联不上。

### 2.2 图片字段名全变了（但结论没变）

原版 §3 里的字段名已经过时。**现在实际是这三个**：

```
customBackground   416,431 B   ← 聊天背景，占 87%
userAvatar          46,551 B
aiAvatar            24,767 B
```

原版猜的 `avatarBase64` / `chatBackgroundBase64` / `splashImageBase64` 那套现在**都不存在**。

⚠️ **但"图片占 99.5%、该拆出去走静态文件"这个结论完全没变** —— 字段名换了，性质一样。

### 2.3 密钥字段现在加密了

原版写的时候没有加密。现在 `server.ts` L171 有：

```ts
const SECRET_FIELDS = ["apiKey", "asrApiKey", "ttsApiKey", "harnessToken"];
```

`loadSettingsFile()` / `saveSettingsFile()` 会分别调 `mapSettingsSecrets(record, "dec" | "enc")` 做**解密 / 加密**，落盘格式是 `enc:v1:<base64>:<base64>`。

⚠️ **迁移时必须二选一，不能两个混着**：

- **方案 A（推荐）**：SQLite 里**存密文原样**，读写时仍然过 `mapSettingsSecrets` —— 改动最小，加密逻辑一行不动
- **方案 B**：迁移时解密后以明文存进 SQLite，再在数据库层做加密 —— 要重写加密路径，风险大

**选 A。** `enc:v1:` 那串就是一个 `TEXT`，SQLite 不关心它是什么。

### 2.4 消息多了几个重字段

原版 §1.4 只说"每条消息收发都全量读写"。**现在消息的单条结构是**（实测第一条的字段）：

```
id, sessionId, role, sender, content, text, reasoningContent, thought,
createdAt, timestamp, elapsedSeconds, attachments, status,
isAgentMode, agentExecution
```

⚠️ **`agentExecution` 是新增的大字段** —— 它存整轮 Agent 执行的过程数据（timeline / steps / 工具调用），
一条可能几 KB 到几十 KB。**建表时给它单独一列，不要和正文混，也不要塞进一个通用 `json` 列**，
否则以后"只看消息列表"和"要看过程详情"会被迫读同一份大字段。

### 2.5 原版缺的两个结构性事实

- **消息没有 `seq` 字段**（原版假设有）。`seq` 是**服务端按数组下标算出来的**，用来做增量拉取游标
  （日志里的 `MSG-PULL afterSeq=9`）。**迁移时要在表里加一个真正的自增列或显式 `seq`**，别再靠下标。
- **会话没有 `deletedAt` 字段**。删除是走 `deletion_signals.json` 的**信号 + 物理删**，
  不做软删。迁移时保持这个语义，**不要顺手加软删**（那会让所有"拉消息"的查询多一个条件，改面很大）。

## 4. 建议：分三期做，不要一次迁完

原版把 6 个文件当一个整体迁。**现在有 9 个，一次迁等于同时改"存储层 + 数据模型 + 加密层"**，
出问题很难定位是哪一层的。

### 第一期：只迁 `settings.json`（约半天）

**为什么先它**：收益最大、风险最小。`check-session` 从「读 490 KB + 解 4 个密钥字段」变成**一条主键查询**。

- 表：`settings(user_id TEXT PRIMARY KEY, data TEXT NOT NULL, updated_at INTEGER)`
- **图片先不拆**，`customBackground` 那几个字段照样存在 `data` 这个 JSON 列里
- 密钥保持 `enc:v1:` 密文原样
- 写锁从全局换成 SQLite 事务

**验收判据**（可复跑）：
1. `GET /api/settings/:userId` 返回的字段跟迁移前**逐字段相同**（用脚本 diff）
2. `check-session` 响应时间从「读 490 KB」降到 **&lt; 5 ms**
3. 重启中继后设置不丢、不改

### 第二期：迁 `messages_v2.json` + `sessions_v2.json`（约一天）

**必须一起迁** —— 消息靠 `sessionId` 关联会话。

- 表：`sessions(id TEXT PRIMARY KEY, user_id TEXT, title, created_at, updated_at, model, workspace, summary, last_summarized_index, is_synced)`
- 表：`messages(id TEXT PRIMARY KEY, session_id TEXT, user_id TEXT, seq INTEGER, role, sender, content, text, reasoning_content, thought, created_at, timestamp, elapsed_seconds, attachments TEXT, status, is_agent_mode INTEGER, agent_execution TEXT)`
- 索引：`(user_id, session_id, seq)`、`(session_id, created_at)`
- **`agentExecution` 单独一列**，别和正文混

**验收判据**：
1. `GET /api/messages/:userId` 返回的条数、顺序、内容跟迁移前一致
2. 增量拉取（`afterSeq`）行为不变
3. 删除一条消息后，`deletion_signals` 行为不变

### 第三期：图片拆出去 + 剩下三个小文件（约半天）

- `customBackground` / `userAvatar` / `aiAvatar` 落盘成静态文件，设置里只存路径
- `pending-decisions.json` / `login_attempts.json` / `deletion_signals.json` / `model_limits.json` / `active_sessions.json` / `users.json` 一起迁

⚠️ **这一期要注意 `active_sessions.json` 的语义**（见 AGENTS.md §4）：
它是**单点登录互斥的真相来源**，`lastActive` 必须落盘（60 秒节流），
`version` 做 CAS。**迁进数据库时这些语义一个都不能丢**。
